# Releasing maelys-json

Releases go through the shared maelys-release socle; `release.yml` and the
managed blocks of `AGENTS.md` and `CLAUDE.md` are generated by
`bin/maelys-release adopt`, never edited by hand. `packaging/release`
declares what this product adds to the socle's defaults: nothing but the
command that keeps the version macros of `include/maelys/json.h` in step
with `VERSION` (`[cut] after-version sh tools/sync-version.sh`).

A release is a signed annotated tag `vX.Y.Z` on `main` whose commit carries
`VERSION` = `X.Y.Z`, the matching header macros and a dated `CHANGELOG.md`
entry. `make check` verifies the three agree.

## With `maelys-release cut` (two stops)

From a maelys-release checkout at the wanted tag, with a dated
`## X.Y.Z — YYYY-MM-DD` entry already in `CHANGELOG.md`:

1. `bin/maelys-release cut /path/to/maelys-json X.Y.Z` prints the plan;
   `--apply` writes `VERSION`, runs `tools/sync-version.sh` so the header
   joins the commit, commits it signed on a release branch, opens the pull
   request and waits for its checks.
2. After the merge, `bin/maelys-release cut /path/to/maelys-json X.Y.Z --tag`
   signs the tag on the merge commit and pushes it.

If the socle moved since the last release, run `adopt --apply` on the
release branch first: an upgrade travels in the commit that prepares the
release, never in a pull request of its own.

## By hand

1. On a `release/X.Y.Z` branch: `VERSION`, `sh tools/sync-version.sh`, date
   the changelog entry, re-adopt the socle if it moved, `make check`.
2. Merge through a pull request with green CI.
3. `bin/maelys-release preflight .` from the socle checkout, then on the
   merge commit: `make check`, `git tag -s vX.Y.Z -m "maelys-json X.Y.Z"`,
   `git push origin vX.Y.Z`.

## After the tag

The workflow verifies the tag, builds Linux x86_64, Linux arm64 and macOS
arm64 with `scripts/package-release.sh TARGET`, attests provenance,
publishes the release, renders `packaging/homebrew/libmaelys-json.rb.in`
and pushes the formula with its bottles to `maelys-dev/homebrew-tap`.

Verify all three, not just the run:

```sh
gh release view vX.Y.Z
gh attestation verify ASSET --repo maelys-dev/maelys-json --signer-repo maelys-dev/maelys-release
gh api repos/maelys-dev/homebrew-tap/contents/Formula/libmaelys-json.rb -q .content | base64 -d | grep tags/
```

The signer is the socle's reusable workflow, hence `--signer-repo`. The
tap job reports success even when it could not push (no credentials): the
formula check is what proves the publication.

## Replaying a tag

A tag whose release or formula failed is replayed in full, never moved or
recreated. Dispatch from the tag itself, or the `release` environment,
limited to tags, refuses the run:

```sh
gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z
```
